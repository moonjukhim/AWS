# Well-Architected Generative AI Lens 기준 보완 항목

대상: A2A Multi-Agent Incident Response (에이전트 3개 코드, CloudFormation 템플릿 4개, Cognito 설정, 프론트엔드 호출 경로)

대부분 코드로 확인한 내용입니다. 학습·분산 컴퓨팅 질문(PERF 3, REL 6)은 이 구조에 해당하는 부분이 적어서 간단히만 적었습니다.

## 우선순위 높은 보완 항목

1. **다른 사용자로 위장 가능 (SEC 1/5)**: 사용자 식별자(actor ID)를 JWT 토큰이 아니라 요청 헤더에서 그대로 받습니다(`host_adk_agent/main.py:31`). 그래서 헤더만 바꾸면 다른 사용자의 메모리 영역에 접근할 수 있습니다.
2. **가드레일 없음 (SEC 2/4)**: Bedrock Guardrails가 전혀 적용돼 있지 않습니다. 웹 검색 결과와 메모리 내용도 검증 없이 프롬프트에 들어갑니다.
3. **시스템 프롬프트가 계속 커짐 (COST 3/SUS 3)**: 사용자 메시지가 올 때마다 메모리 내용을 시스템 프롬프트에 덧붙이고, 이전에 붙인 내용은 지우지 않습니다(`monitoring_strands_agent/memory_hook.py:78`, `:152`).
4. **IAM 와일드카드 (SEC 1)**: `secretsmanager:GetSecretValue`와 `GetResourceOauth2Token`이 `Resource: '*'`입니다. 템플릿에도 `# TODO: Scope down`이 남아 있습니다(`cloudformation/host_agent.yaml:111`, `:118`).
5. **업데이트 배포 경로 없음 (OPS 4)**: `deploy.py`는 스택 생성만 합니다. 스택이 이미 있으면 그냥 넘어가서 변경 사항이 반영되지 않습니다. 이 폴더는 git 저장소도 아닙니다.

## 지속가능성 (Sustainability)

### SUS 1. 컴퓨팅 리소스 최소화
- 현재 잘 된 점: AgentCore Runtime은 서버리스입니다. CodeBuild와 컨테이너도 ARM 기반(Graviton)을 씁니다.
- 보완:
  - 에이전트 3개와 메모리 추출이 모두 Sonnet 4.5입니다. 모니터링·웹검색 하위 에이전트와 메모리 추출에는 Haiku 급 소형 모델을 검토하세요.
  - CodeBuild가 `BUILD_GENERAL1_LARGE`입니다. 이미지 빌드에는 MEDIUM이면 충분할 가능성이 큽니다.
  - Runtime의 유휴 세션 타임아웃(`LifecycleConfiguration`)을 명시해서 쓰지 않는 microVM을 빨리 회수하세요.

### SUS 2. 데이터 처리·저장 최적화
- 현재 잘 된 점: 로그 보존 30일, ECR 수명 주기 정책, 메모리 이벤트 만료 60일이 설정돼 있습니다.
- 보완:
  - Host 이미지에 google-adk가 끌고 오는 GCP 라이브러리(spanner, bigquery, aiplatform 등)가 대량으로 들어갑니다. 불필요한 패키지를 제거하면 이미지 크기와 빌드·콜드스타트 에너지가 줄어듭니다.
  - S3 버킷에 수명 주기 정책이 없습니다.
  - Tavily 결과 본문을 길이 제한 없이 그대로 넘깁니다.

### SUS 3. 모델 효율성 유지
- 현재 잘 된 점: Gateway의 시맨틱 도구 검색(`SearchType: SEMANTIC`)으로 도구 목록 토큰을 줄이고 있습니다.
- 보완:
  - 우선순위 3번의 시스템 프롬프트 누적 문제를 고치세요.
  - Bedrock 프롬프트 캐싱을 시스템 프롬프트에 적용하세요.

## 운영 우수성 (Operational Excellence)

### OPS 1. 출력 품질 일관성 검증
- 현재: `test/connect_agent.py`는 연결 테스트뿐입니다. 품질 평가가 없습니다.
- 보완:
  - 대표 장애 시나리오로 정답셋(golden dataset)을 만드세요. 예: EC2 CPU 급증, Lambda 오류, RDS 연결 타임아웃.
  - LLM-as-judge나 AgentCore Evaluations로 회귀 평가를 하고, 배포 게이트로 사용하세요.
  - 평가 지표는 도구 호출 정확도와 근거(지표 수치) 인용 여부를 우선 보세요.

### OPS 2. 운영 상태 모니터링
- 현재 잘 된 점: OTEL 계측, X-Ray 트레이스, 로그 전송이 설정돼 있습니다.
- 보완:
  - 에이전트별 오류율, 지연 시간, 스로틀링, 토큰 사용량에 대한 CloudWatch 알람과 대시보드가 없습니다.
  - 메모리 훅의 예외는 로그만 남기고 삼킵니다. 실패 횟수를 지표로 내보내세요.

### OPS 3. 모델·프롬프트·자산 추적성
- 현재 잘 된 점: 모델 ID가 CFN 파라미터입니다. Host와 웹검색 ECR은 태그 변경 불가(IMMUTABLE)입니다.
- 보완:
  - git으로 버전 관리를 시작하세요.
  - 프롬프트가 코드에 하드코딩돼 있습니다. Bedrock Prompt Management나 버전이 붙은 파일로 분리하세요.
  - 트레이스에 모델 ID와 프롬프트 버전을 속성으로 기록하세요.
  - 모니터링 에이전트 ECR은 IMMUTABLE이 아닙니다.
  - Dockerfile의 `uv:latest`를 특정 버전으로 고정하세요.

### OPS 4. 수명 주기 자동화
- 현재: 대화형 `deploy.py`로 생성만 가능합니다.
- 보완:
  - CodePipeline이나 GitHub Actions에서 평가 후 배포하도록 구성하세요.
  - CloudFormation 변경 세트로 업데이트하세요.
  - AgentCore Runtime 버전과 엔드포인트로 카나리 배포와 롤백 경로를 만드세요. 지금 프론트엔드는 `qualifier=DEFAULT`로 고정입니다.

### OPS 5. 모델 맞춤 설정 시점 판단
- 현재: 맞춤 설정 없이 프롬프트, 도구, 메모리로 해결하고 있습니다. 적절한 선택입니다.
- 보완: 판단 기준을 문서화하세요. 예를 들어 OPS 1의 평가 지표가 프롬프트·도구·검색 개선 후에도 지속적으로 기준 미달일 때만 미세 조정을 검토하는 식입니다.

## 비용 최적화 (Cost Optimization)

### COST 1. 적절한 모델 선택
- 역할별로 모델을 다르게 쓰세요. 오케스트레이터만 상위 모델, 하위 에이전트와 메모리 추출은 소형 모델입니다.
- 모델 ID가 이미 파라미터로 분리돼 있어서 바꾸기 쉽습니다. 바꾸기 전에 OPS 1 평가로 품질을 확인하세요.

### COST 2. 가격 모델 선택
- 현재: 온디맨드 + global 교차 리전 추론 프로필입니다. 사용량이 들쭉날쭉한 이 워크로드에 맞습니다.
- 보완:
  - 리소스 태그가 `Name`뿐입니다. Project, Env 같은 비용 할당 태그를 추가해 에이전트별 비용을 보이게 하세요.
  - 사용량이 일정 수준을 넘을 때만 프로비저닝 처리량을 검토하세요.

### COST 3. 비용 최적화 프롬프트 설계
- 우선순위 3번의 시스템 프롬프트 누적을 고치세요.
- 프롬프트 캐싱을 적용하세요.
- `max_tokens` 상한을 설정하세요.
- Tavily `max_results`를 기본 5에서 더 줄이고 본문 길이를 자르세요.
- Host가 하위 에이전트에 넘기는 컨텍스트를 요약하세요.

### COST 4. 벡터 스토리지 최적화
- 별도 벡터 DB 없이 AgentCore Memory의 시맨틱 전략을 쓰고 있습니다.
- 보완:
  - 웹검색 에이전트에 LLM이 마음대로 메모리를 저장하는 도구가 열려 있습니다(`save_custom_memory`, `web_search_openai_agents/memory_tool.py:166`). 메모리가 제한 없이 쌓일 수 있으니 도구를 줄이세요.
  - 60일 보존이 정말 필요한지 재검토하세요.

### COST 5. 에이전트 워크플로 최적화
- 시스템 프롬프트가 "항상 monitor 먼저, 그다음 websearch"를 강제합니다. 그래서 단순 조회에도 LLM 호출이 2단계 이상 일어납니다. 질문 유형에 따라 조건부로 라우팅하세요.
- 에이전트별 최대 반복 횟수를 제한하세요.
- 같은 검색 질의 결과를 캐싱하세요.

## 성능 효율성 (Performance Efficiency)

### PERF 1. 운영 성능 측정·개선
- 첫 토큰 시간(TTFT), 전체 지연 시간, 도구 호출 지연, 에이전트별 토큰 수를 OTEL 트레이스에서 지표로 뽑으세요.
- 목표 수준(SLO)을 정의하세요.

### PERF 2. 허용 성능 유지
- Host와 하위 에이전트 사이가 `streaming=False`입니다. 그래서 하위 에이전트가 끝날 때까지 사용자는 아무 응답도 받지 못합니다.
- 하위 에이전트는 텍스트 조각이 올 때마다 누적된 전체 텍스트를 다시 보냅니다(`monitoring_strands_agent/agent_executor.py:90`, `web_search_openai_agents/agent_executor.py:73`). 응답이 길어질수록 전송량이 제곱으로 늘어납니다.
- 첫 요청 때 에이전트 카드 조회와 SSM 조회가 모두 일어납니다. 콜드스타트를 측정하고 부하 테스트를 하세요.

### PERF 3. 분산 컴퓨팅 리소스 최적화
- 학습이나 분산 작업이 없어서 해당 부분이 적습니다.
- CodeBuild 규모 조정과 Runtime 동시 세션 할당량 확인 정도면 충분합니다.

### PERF 4. 데이터 검색 성능
- 메모리 관련도 임계값이 0.2와 0.3으로 낮아서 관련 없는 내용이 섞일 수 있습니다. 평가로 튜닝하세요.
- Tavily `include_domains`가 비어 있습니다(`web_search_openai_agents/tools.py:39`). `docs.aws.amazon.com`, `repost.aws` 등으로 제한하면 정확도가 오릅니다.
- AWS 공식 문서용 MCP 서버를 쓰는 것도 고려하세요.

## 신뢰성 (Reliability)

### REL 1. 처리량 할당량 결정
- 에이전트 3개와 메모리 추출이 같은 모델의 계정 할당량(TPM/RPM)을 함께 씁니다.
- 1회 사용자 요청당 LLM 호출 수를 측정하세요. 그 값으로 필요 할당량을 계산하고 Service Quotas로 증설을 요청하세요.
- Tavily 요청 한도와 Runtime 동시 세션 한도도 함께 확인하세요.

### REL 2. 구성 요소 간 안정적 통신
- 현재 잘 된 점: A2A 통신에 에이전트별 M2M JWT를 씁니다.
- 보완:
  - `force_authentication=True` 때문에 클라이언트를 만들 때마다 토큰을 새로 발급받습니다(`host_adk_agent/agent.py:45`). 토큰을 캐싱하세요.
  - 모니터링 에이전트는 첫 요청 때 받은 workload 토큰을 계속 씁니다(`monitoring_strands_agent/agent.py:31`). 세션이 길면 토큰이 만료될 수 있으니 확인이 필요합니다.
  - 하위 에이전트가 실패해도 부분 결과로 답하도록 Host에 방어 로직을 넣으세요.

### REL 3. 재시도·실패 복구
- LLM, A2A, Tavily 호출 모두 명시적인 재시도·백오프가 없습니다.
- 오류 처리 코드 자체에 버그가 있습니다.
  - `monitoring_strands_agent/agent.py:75`: `raise f"..."`는 문자열을 raise해서 원래 오류 대신 TypeError가 납니다.
  - `web_search_openai_agents/agent_executor.py:113`: `Exception(error=...)`도 TypeError입니다. 그 위의 `actor_id`는 경우에 따라 정의되지 않은 상태로 쓰입니다.
- 세션 저장소(`InMemorySessionService`)와 작업 저장소(`InMemoryTaskStore`)가 메모리 기반이라 재시작하면 상태가 사라집니다.

### REL 4. 프롬프트·파라미터·모델 버전 관리
- 모델 ID 파라미터화와 패키지 버전 고정(requirements.txt)은 잘 돼 있습니다.
- 프롬프트, 메모리 추출 프롬프트(CFN 안에 있음), 모델 ID를 하나의 릴리스 단위로 묶어 버전을 붙이세요.
- Runtime 버전으로 롤백할 수 있게 하세요.

### REL 5. 추론 워크로드 분산
- global 추론 프로필 덕분에 모델 추론은 이미 여러 리전으로 분산됩니다.
- 반면 Runtime, Memory, Gateway는 us-west-2 단일 리전이고, 리전이 `deploy.py`와 Dockerfile에 하드코딩돼 있습니다.
- 재해 복구가 필요하면 리전을 파라미터로 바꾸고 보조 리전 배포를 준비하세요.

### REL 6. 분산 작업의 완료율 극대화
- 학습 작업에는 해당하지 않습니다.
- 에이전트 워크플로 관점에서는 단계 수 상한, 단계별 타임아웃, 부분 결과 반환을 설계하세요.

## 보안 (Security)

### SEC 1. 엔드포인트 접근 관리
- 현재 잘 된 점: Runtime마다 Cognito JWT 인증, 에이전트별 M2M 클라이언트, 웹은 PKCE 방식입니다.
- 보완:
  - actor ID를 헤더가 아니라 JWT의 `sub` 클레임에서 가져오세요.
  - Cognito MFA가 `OFF`입니다(`cloudformation/cognito.yaml:41`).
  - 웹 클라이언트 리프레시 토큰이 30일입니다(`cloudformation/cognito.yaml:193`). 줄이는 것을 검토하세요.
  - IAM 와일드카드를 좁히세요: `secretsmanager:*`, OAuth 토큰, `ssm:parameter/*`.
  - Runtime 네트워크가 `PUBLIC`입니다. VPC 모드를 검토하세요.
  - Tavily 키가 `NoEcho` 없는 CFN 파라미터이고, Runtime 환경변수에 평문으로 들어갑니다. Secrets Manager나 AgentCore Identity로 옮기세요.

### SEC 2. 유해·편향·사실과 다른 답변 방지
- Bedrock Guardrails가 없습니다. 콘텐츠 필터, 프롬프트 공격 필터, 문맥 근거(contextual grounding) 검사를 적용하세요.
- 프롬프트에 "실제 도구 결과에 있는 지표만 인용하라"는 규칙을 넣고, OPS 1 평가로 검증하세요.

### SEC 3. 이벤트 모니터링·감사
- Bedrock 모델 호출 로깅이 꺼져 있습니다. 켜서 S3나 CloudWatch에 저장하세요.
- CloudTrail로 AgentCore와 Bedrock API 호출을 감사하세요.
- 사용자 메시지 원문을 그대로 로그에 남깁니다(`monitoring_strands_agent/agent_executor.py:159`, `web_search_openai_agents/agent_executor.py:138`). 개인정보를 마스킹하세요.
- 로그 그룹에 KMS 암호화를 적용하세요.

### SEC 4. 시스템·사용자 프롬프트 보호
- 신뢰할 수 없는 메모리 내용을 시스템 프롬프트에 직접 넣고 있습니다(`monitoring_strands_agent/memory_hook.py:78`). 시스템 지시와 같은 권한을 갖게 되므로, 구분자를 둔 사용자 메시지 쪽으로 옮기세요.
- 오류가 나면 예외 원문이 사용자 응답으로 나갑니다. 내부 정보가 노출되지 않게 일반 메시지로 바꾸세요.
- 웹 검색 결과를 통한 간접 프롬프트 인젝션은 Guardrails의 프롬프트 공격 필터로 대응하세요.

### SEC 5. 과도한 에이전시 방지
- 현재 잘 된 점: 모니터링 도구가 CloudWatch 조회 전용입니다.
- 보완:
  - Gateway 역할이 `Resource: '*'`라서 계정 안의 모든 로그 그룹을 읽을 수 있습니다. 대상 로그 그룹으로 좁히세요.
  - 웹검색 에이전트의 메모리 쓰기 도구를 제거하거나 제한하세요.
  - Host의 단계 수에 상한을 두세요.
  - 나중에 조치(쓰기) 도구를 추가한다면 사람의 승인 단계를 넣으세요.

### SEC 6. 데이터 오염 탐지·대응
- 오염 경로가 하나 있습니다. 웹 콘텐츠 → 에이전트 → `save_custom_memory` → 장기 메모리 → 이후 세션의 시스템 프롬프트 순서입니다.
- 메모리 쓰기를 제한하세요.
- 추출 결과를 검증하세요. 추출 프롬프트에 "사용자가 명시한 사실만"이라는 조건이 있는 것은 좋은 점입니다.
- 오염된 항목을 삭제하는 절차를 마련하세요.
- Smithy 모델과 에이전트 소스 zip이 같은 S3 버킷에 있고, CodeBuild가 그 소스를 빌드합니다. 버킷 버전 관리와 쓰기 권한 제한으로 공급망 변조를 막으세요.
