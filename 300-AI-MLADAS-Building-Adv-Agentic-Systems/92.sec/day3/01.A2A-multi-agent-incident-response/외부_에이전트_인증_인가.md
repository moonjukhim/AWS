# 다른 조직·다른 인프라 에이전트의 인증과 인가

다른 조직이나 다른 인프라의 에이전트와 연동할 때는 **방향을 둘로 나눠서** 설계합니다. 외부 에이전트가 우리를 호출하는 경우(인바운드)와 우리가 외부 에이전트를 호출하는 경우(아웃바운드)입니다.

이 문서는 현재 프로젝트 구조를 그대로 확장하는 방식으로 설명합니다. 현재 구조는 Cognito JWT 인증 + AgentCore Identity로 M2M 토큰을 발급받는 방식입니다.

## 1. 인바운드: 외부 에이전트가 우리 에이전트를 호출할 때

상대가 어떤 인프라에 있느냐에 따라 인증 방식을 고릅니다.

| 상대 환경 | 추천 방식 | 구현 |
|---|---|---|
| IdP가 없는 파트너, 소규모 연동 | **우리 IdP에서 클라이언트 발급** | `cognito.yaml`에 파트너 전용 App Client(client credentials)를 추가하고, Runtime의 `AllowedClients`에 그 ID를 넣습니다. 지금 에이전트 간 M2M 구조와 같습니다. |
| 자체 OIDC IdP가 있는 조직 (Okta, Entra ID, 다른 클라우드) | **연합(federation) 또는 토큰 교환** | Runtime의 `CustomJWTAuthorizer`는 Runtime 하나에 `DiscoveryUrl`을 하나만 받습니다. 그래서 파트너 IdP 전용 Runtime 엔드포인트를 따로 두거나, 중간에 토큰 교환(RFC 8693) 브로커를 둡니다. 브로커는 파트너 토큰을 검증한 뒤 우리 토큰으로 바꿔 줍니다. |
| 다른 AWS 계정 | **교차 계정 IAM 역할** | 우리 계정에 역할을 만들고, 그 역할에 특정 Runtime ARN에 대한 `bedrock-agentcore:InvokeAgentRuntime`만 허용합니다. 상대는 `ExternalId` 조건을 걸고 이 역할을 AssumeRole해서 SigV4 서명으로 호출합니다. 이 경우 Runtime은 JWT가 아니라 IAM 인증으로 구성해야 합니다. |
| mTLS가 필수인 금융·공공 기관 | **프록시 앞단 배치** | API Gateway 사용자 지정 도메인의 mTLS 기능으로 인증서를 검증한 뒤 Runtime으로 전달합니다. |

어느 방식이든 A2A **Agent Card의 `securitySchemes`**에 요구하는 인증 방식을 선언하세요. A2A는 OAuth2, OIDC, Bearer, API Key, mTLS를 지원합니다. 그래야 상대 클라이언트가 카드를 읽고 맞는 방식으로 붙습니다. 지금 각 에이전트 `main.py`의 AgentCard에는 이 선언이 없습니다.

## 2. 아웃바운드: 우리 Host가 외부 에이전트를 호출할 때

지금 Host가 하위 에이전트를 부르는 방식을 그대로 쓰면 됩니다. 핵심은 **비밀값을 코드에 두지 않고 AgentCore Identity에 맡기는 것**입니다.

1. 파트너에게 client ID/secret과 토큰 엔드포인트를 받습니다.
2. AgentCore Identity에 OAuth2 자격 증명 공급자를 등록합니다.
   ```bash
   aws bedrock-agentcore-control create-oauth2-credential-provider \
     --name partner-x-provider \
     --credential-provider-vendor CustomOauth2 \
     --oauth2-provider-config-input '{...파트너 discovery URL, client id/secret...}'
   ```
   API Key 방식인 상대라면 API Key 공급자로 등록합니다.
3. Host 코드(`host_adk_agent/agent.py`)에서는 기존 `_create_client_factory`에 공급자 이름만 바꿔 넣습니다.
   ```python
   partner_agent = RemoteA2aAgent(
       name="partner_agent",
       agent_card="https://partner.example.com/.well-known/agent-card.json",
       a2a_client_factory=_create_client_factory(
           provider_name="partner-x-provider", session_id=session_id, actor_id=actor_id),
   )
   ```
   토큰 발급과 갱신은 `@requires_access_token`이 처리합니다.
4. 상대의 Agent Card는 신뢰할 수 있는 URL에서만 가져오세요. 상대가 제공하면 A2A v0.3의 카드 서명(`signatures`)도 검증하세요.

## 3. 인가: 인증을 통과한 상대에게 무엇을 허용할지

인증은 "누구인가"까지만 확인합니다. 외부 조직과 연동할 때는 인가 설계가 더 중요합니다.

- **스코프로 기능 제한**: Cognito Resource Server에 기능별 커스텀 스코프를 정의하세요. 예: `incident/logs.read`, `incident/websearch`. 파트너 클라이언트에는 필요한 스코프만 부여하고, 에이전트 코드에서 JWT의 `scope`를 확인해 허용된 skill만 실행하세요.
- **신원은 검증된 토큰에서만 가져오기**: 테넌트와 사용자 식별자는 헤더가 아니라 검증된 JWT 클레임(`client_id`, `sub`)에서 꺼내세요. 지금 프로젝트처럼 헤더의 actor ID를 그대로 믿으면(`host_adk_agent/main.py:31`) 외부 조직이 다른 조직의 메모리에 접근할 수 있습니다. `보완.md`의 SEC 1 항목입니다.
- **테넌트별 데이터 분리**: 메모리 namespace를 검증된 `client_id` 기준으로 나누세요. 예: `/tenant/{clientId}/...`.
- **최종 사용자 권한 전달**: 파트너의 최종 사용자 권한으로 동작해야 한다면, 에이전트 자격이 아니라 토큰 교환(on-behalf-of)으로 사용자 문맥을 담은 토큰을 받아서 넘기세요.
- **도구 단위 정책**: 외부 호출이 Gateway 도구까지 이어진다면 Gateway 앞단에서 도구 호출을 정책으로 제한하세요. AgentCore에는 Cedar 기반 정책 기능이 있지만, 사용 가능 여부는 리전별로 확인이 필요합니다.

## 4. 운영과 데이터 경계

- **토큰과 키 관리**: 토큰 수명을 짧게 두고(지금 M2M은 1시간으로 적절합니다), 파트너별 secret을 정기적으로 교체하세요. 계약이 끝나면 클라이언트를 즉시 비활성화하세요.
- **사용량 제한**: 파트너별로 호출량을 제한하세요(API Gateway 사용량 계획 등). 상대 쪽 무한 루프가 우리 Bedrock 할당량을 소진할 수 있습니다.
- **감사**: 로그와 트레이스에 `client_id`를 남겨서 조직별 호출을 추적하세요.
- **응답은 신뢰하지 않기**: 외부 에이전트의 응답은 신뢰할 수 없는 입력입니다. 간접 프롬프트 인젝션에 대비해 Guardrails를 거쳐 받으세요.
- **보내는 데이터 최소화**: 외부로 보내는 내용에서 계정 ID, ARN, 로그 원문 같은 민감 정보를 최소화하세요.

## 정리

- 소규모 파트너: 우리 Cognito에서 전용 클라이언트를 발급하고 스코프로 제한하는 방식이 가장 빠르고, 지금 구조를 거의 그대로 씁니다.
- 자체 IdP를 쓰는 대규모 조직: 토큰 교환 브로커가 관리 부담이 적습니다.
- 같은 AWS 생태계: 교차 계정 IAM 역할이 관리 부담이 적습니다.
