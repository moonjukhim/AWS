1. 도입: 왜 에이전트에 Well-Architected를 따로 적용하나 (슬라이드 1–3)

1.1 시나리오 소개 (3분)

이 모듈 전체에서 쓸 "평가 대상 시스템"을 먼저 보여 줍니다. images/high-level-arch.png나 images/demo.gif를 띄우고 흐름을 한 줄씩 짚습니다.

외부 시스템(Jira/PagerDuty 등) ─ 티켓 JSON ─▶ SNS 토픽
  ─▶ Trigger Lambda (필드 검증 · DDB 멱등 저장 · 실패 시 DLQ)
  ─▶ AgentCore Runtime (Strands 에이전트, 컨테이너)
       ① Guardrail로 PII·프롬프트 공격 정제
       ② Memory에서 이 요청자의 과거 장애 요약 조회
       ③ 우선순위로 모델 선택 (LOW → Haiku, 그 외 → Sonnet)
       ④ Gateway(MCP)로 도구 연결
       ⑤ LLM이 진단: lookup_user → get_process_info → query_kb → create_change_request
       ⑥ 결과를 DynamoDB에 기록  ⑦ EventBridge로 TicketResolved 발행
  ─▶ AgentCore Gateway (IAM 인증 · 시맨틱 검색 · Cedar Policy Engine)
       ─▶ Lambda 도구 4개 ─▶ DynamoDB 4개 테이블 / Bedrock Knowledge Base(S3 Vectors)

강조할 점: 이 에이전트는 사람이 보지 않는 상태에서 이벤트 하나로 시작해, 변경 요청(Change Request)을 실제로 기록하는 시스템입니다. 채팅봇보다 자율성이 높고, 그래서 Well-Architected 관점의 점검이 필요합니다.

1.2 이 샘플을 고른 이유

  • README가 직접 "AgentCore 서비스 6종"(Runtime, Gateway+Policy, Memory, Identity, Observability, Evaluations)과 "복원력 기능 10종"을 표로 정리해 둡니다(README.md:160-184).
  • docs/design-decisions.md에 ADR 10개가 있습니다. 각 ADR에 "왜"와 "트레이드오프"가 적혀 있어서, Well-Architected 리뷰에서 "이 결정의 트레이드오프는?"을 물을 때 근거로 쓸 수 있습니다.
  • README의 "Scale for Production" 절(README.md:736)이 개발 설정에서 프로덕션 설정으로 바꿀 항목을 나열해 두었습니다. 슬라이드 11의 체크리스트와 바로 연결됩니다.

슬라이드 3 고려 사항 이 샘플에서의 모습 구현 위치

2.2 Generative AI Lens: "필요한 경우에만 대리권을 높인다" (슬라이드 6)

이 원칙을 코드로 보여 주기 가장 좋은 곳은 main.py의 메인 흐름입니다. 무엇을 LLM에게 맡기고 무엇을 코드로 고정했는지 나눠 보면 원칙이 바로 보입니다.

단계 누가 하나 위치 이유
입력 검증, DDB 저장 코드 (Trigger Lambda) ticket_event_handler.py:52-107 판단이 필요 없는 일
PII·프롬프트 공격 정제 코드 (Guardrail API) main.py:262-291, :460-467 보안 경계는 결정적이어야 함

모델 선택 코드 (규칙) model/load.py:15-30 우선순위라는 명시적 신호가 있음
진단, 도구 선택, 조치 여부 판단 LLM main.py:561-570 여기만 추론이 필요함
결과 저장, 이벤트 발행 코드 main.py:590-604 LLM이 "저장했다"고 말하는 것을 믿지 않음

핵심 메시지: 에이전트라고 해서 모든 단계를 LLM에게 맡기지 않습니다. 이 샘플에서 LLM이 정하는 것은 "어떤 도구를 어떤 순서로 호출하고, 조치를 할지 말지" 뿐입니다. 나머지는 워크플로처럼 코드로 고정되어 있습니다.

토론 질문: "SYSTEM_PROMPT(main.py:93-115)가 도구 호출 순서 1→2→3→4를 이미 지시하고 있습니다. 그렇다면 이것은 에이전트입니까, 워크플로입니까?" 답의 방향: 순서는 프롬프트로 권장할 뿐 강제하지 않습니다. get_process_info는 "티켓에 서비스 이름이 있을 때만", create_change_request는 "런북이 근거가 될 때만" 호출하는 조건부 판단이 LLM에게 남아 있습니다. 이 정도가 "필요한 만큼의 대리권"입니다.

2.3 Agentic AI Security Scoping Matrix (슬라이드 7)

이 샘플의 위치: 감독되는 대리권 (Scope 3)

  • 실행은 외부 이벤트(SNS 티켓)가 시작합니다. 에이전트가 스스로 작업을 만들지는 않으므로 Scope 4(전체 대리권)는 아닙니다.
  • 그런데 시작된 뒤에는 create_change_request라는 쓰기 작업을 사람 승인 없이 실행합니다. 그래서 Scope 2(규정된 대리권)도 아닙니다.
수준을 바꾸려면 필요한 변경 샘플 기준 구체적 방법
Scope 3 → Scope 2로 낮추기 쓰기 작업 전에 사람 승인 create_change_request.py가 status: "applied" 대신 "pending_approval"을 기록하고, 승인 시스템이 EventBridge 이벤트를 받아 처리
Scope 3 안에서 통제 강화 정책을 실제로 적용 agentcore.json의 policyEngineConfiguration.mode를 LOG_ONLY → ENFORCE
Scope 4로 높인다면 필요한 것 자체 시작, 지속 모니터링 이상 탐지 시 에이전트가 스스로 티켓 생성 → 이때는 행동 드리프트 탐지, 속도 제한, 킬 스위치가 필수

핵심 메시지: 슬라이드 노트대로 "대부분의 프로덕션 시스템은 Scope 2나 3에서 시작"합니다. 이 샘플이 Policy Engine을 LOG_ONLY로 두는 이유(ADR-7: "막기 전에 무엇이 막힐지 먼저 본다")도 같은 맥락입니다.

2.4 에이전틱 AI용 Well-Architected 원칙 6가지 (슬라이드 8)

슬라이드 노트의 마지막 질문("관찰할 수 있습니까? 제어할 수 있습니까? …")을 이 샘플에 그대로 던집니다.

원칙 질문 샘플의 답 빈틈
관찰성 관찰할 수 있는가? OTEL 자동 계측 + ticket.id, ticket.priority, ticket.requester_id, ticket.mode 스팬 속성(main.py:430-438). 단계별 SSE 이벤트(_stage_event, main.py:313) 도구 실행 시간 훅(main.py:66-81)이 프롬프트 모드에서만 등록됨(:383-384). 티켓 처리 경로(:515)에는 없음
제어 가능성 제어할 수 있는가? Cedar 정책, Gateway를 거치지 않으면 도구 호출 불가, 도구 Lambda의 입력 검증(create_change_request.py:56-90) 정책이 LOG_ONLY라 실제로 막지는 않음
진실성·강건성 정확하고, 이상 입력에 견디는가? 런북(KB) 근거가 있을 때만 조치하도록 지시. 잘못된 페이로드는 구조화된 실패 응답(main.py:417-423). 결과가 비면 자동 종결하지 않고 Failed 처리(:577-581) 응답이 런북 내용과 일치하는지 검증하는 단계 없음 (온라인 평가 Correctness로 사후 확인만 가능)
공정성 사용자 그룹별로 다르게 대하지 않는가? 모델 라우팅 기준이 사용자가 아니라 티켓 우선순위 priority를 요청자가 직접 넣음 → 우선순위를 부풀리면 더 좋은 모델을 받게 됨. 반대로 LOW로 분류된 사용자 그룹이 체계적으로 낮은 품질을 받는지 모니터링 필요
투명성 동작이 문서화되어 있는가? ADR 10개(docs/design-decisions.md), 단계별 아키텍처 문서(docs/ARCHITECTURE.md), 변경 요청에 reason 필드 기록 최종 해결 코멘트는 사고 과정을 빼도록 지시함 → 감사용 근거는 트레이스에서 확인해야 함
거버넌스 관리되고 있는가? 정책을 코드로 선언(policyEngines), validationMode 설정, 온라인 평가로 지속 모니터링 정책 변경 승인 절차나 AWS Config 규칙은 없음

강사 팁: "공정성" 행은 수강생이 잘 떠올리지 못합니다. "우선순위 필드를 누가 채우는가?"라고 물으면, 비용 최적화 설계(ADR-8)가 공정성 문제와 연결된다는 점을 스스로 찾아냅니다. 해결책은 우선순위를 요청자 입력 대신 분류기(Haiku)가 다시 판정하게 하는 것입니다.

4.2 보안 (슬라이드 18)

슬라이드 고려 사항 슬라이드의 접근 방식 샘플 구현 빈틈 / 개선 과제

// 모든 도구 호출 허용 (기본 허용 + 로그)
permit(principal, action, resource is AgentCore::Gateway);

// 사유(reason) 없이 변경 요청을 만들면 거부

when { context has "toolName" && context.toolName == "create-change-request"

설명 순서: 1. forbid는 permit보다 우선합니다. 그래서 "기본 허용 + 위험 작업만 거부" 패턴이 됩니다. 2. reason 필드는 도구 스키마(tool-schemas/create-change-request.json)에서는 선택 항목입니다. 스키마는 느슨하게, 정책은 엄격하게 두어 "거버넌스 규칙을 도구 코드가 아니라 정책 계층에서 관리"하는 예입니다. 3. 지금은 LOG_ONLY라 위반이 로그에만 남습니다. 동시에 도구 Lambda마다 IAM 권한이 따로 있어서(lookup_user는 읽기 전용, create_change_request만 쓰기) 정책이 꺼져 있어도 심층 방어가 유지됩니다(ADR-7).

(1) 재시도 SNS → Lambda 비동기 호출의 자동 재시도, 이후 DLQ infra-construct.ts:423-444
(2) 대체 도구 Gateway 또는 Jira 연결이 실패해도 살아 있는 도구만으로 진행 mcp_client/client.py:150-198

tickets_table.put_item(Item=sanitized,

# 도구: 변경 기록과 사용자 카운터를 한 트랜잭션으로 (create_change_request.py:102)
_ddb.transact_write_items(TransactItems=[{"Put": ...}, {"Update": ...}])

create_change_request.py:95-101의 주석이 "두 번 나눠 쓰면 일부만 성공할 수 있고, 모델이 재시도하면 변경 기록이 중복된다"고 이유를 설명합니다. LLM은 같은 도구를 다시 호출할 수 있다는 점이 일반 애플리케이션과 다른 신뢰성 고려 사항입니다.

개선 과제: 타임아웃 계층 추가. 슬라이드는 도구 5–30초, 추론 30–60초, 턴 2–5분, 세션 15분을 제시합니다. 샘플은 도구(Lambda 15/30초)만 있습니다. 에이전트 실행 전체에 상한을 두는 예:

import asyncio

async with asyncio.timeout(300):   # 대화 턴 상한 5분 (Python 3.11+)
    async for event in agent.stream_async(user_query):
        ...
# TimeoutError → 기존 except 블록이 _fail_ticket()으로 사람 검토에 넘김

토론 질문: "SNS → Lambda 재시도는 Runtime 호출이 실패했을 때 일어납니다. DDB 저장은 멱등이지만 Runtime 호출은 멱등입니까?" → 재시도 시 에이전트가 같은 티켓을 두 번 처리할 수 있습니다. create_change_request 앞에서 "이 티켓에 이미 변경 요청이 있는가"를 확인하거나, 티켓 상태를 Processing으로 조건부 갱신한 뒤 시작하는 방법을 토론합니다.

4.4 성능 효율성 (슬라이드 20)

슬라이드 고려 사항 슬라이드의 접근 방식 샘플 구현 빈틈 / 개선 과제
컨텍스트 윈도우 최적화 Memory로 대화 기록 외부화, 프롬프트 캐싱, Strands 대화 관리자 과거 장애 전체 대화가 아니라 요약 상위 5개만 시스템 프롬프트에 주입(ADR-4, enrichment.py:36). 티켓 1건 = 세션 1개라 대화가 길어지지 않음 프롬프트 캐싱 없음. 대화 관리자는 Strands 기본값
다중 에이전트 성능 분산 Runtime 종량제·자동 확장, 전문가 에이전트 독립 확장 단일 에이전트. Runtime이 세션 단위로 확장 분류(Haiku) → 해결(Sonnet) 에이전트 분리 시 독립 확장 가능
도구 설계 효율성 Gateway 시맨틱 검색, 정보 집약형 도구, 중앙화, Lambda 프로비저닝 동시성 enableSemanticSearch: true. lookup_user가 프로필 + 쿼터 + 최근 30일 티켓을 한 번에 반환(정보 집약형) 프로비저닝 동시성 없음 (비동기 처리라 콜드 스타트 영향 작음, ADR-2)

보여 줄 코드: 정보 집약형 도구 (lambdas/tools/lookup_user.py 반환값)

{"user_id": ..., "profile": user, "quotas": ...,
 "recent_tickets": [...], "recent_incident_count_30d": len(recent)}

도구를 get_profile, get_quotas, get_recent_tickets 3개로 쪼갰다면 LLM 왕복이 3번 필요하고, 매 왕복마다 컨텍스트 전체를 다시 처리합니다. 도구 하나가 판단에 필요한 정보를 한 번에 주는 것이 슬라이드의 "단일 상호 작용에서 계층적 JSON 반환"입니다.

메모리 설계 보충 (memory/enrichment.py) - SUMMARIZATION 전략은 incidents/{actorId}/{sessionId}에 저장하고, 조회는 incidents/{requester_id} 접두사로 합니다. 그래서 한 사용자의 모든 세션 요약이 검색됩니다. - 요약은 비동기로 만들어지므로 방금 제출한 티켓은 바로 보이지 않습니다. 그래서 main.py:149-179의 _count_recent_incidents가 DynamoDB를 직접 조회해 재발 횟수를 보완합니다. "Memory는 의미 검색용, 강한 일관성이 필요한 숫자는 DB"라는 역할 분담입니다.

개선 과제: 프롬프트 캐싱. 이 에이전트의 시스템 프롬프트와 도구 정의는 티켓마다 같으므로 캐싱 효과가 큽니다. Strands에서는 시스템 프롬프트를 콘텐츠 블록 목록으로 주고 캐시 지점을 표시하는 방식이 있습니다. 파라미터 이름은 Strands 버전마다 다를 수 있으니 수업 전에 설치된 버전(uv.lock 기준 strands-agents 1.42.0)의 문서를 확인하세요.

agent = Agent(
    model=load_model(priority),
    system_prompt=[{"text": SYSTEM_PROMPT}, {"cachePoint": {"type": "default"}}],
    tools=tools,
)

주의: 이 샘플은 과거 장애 요약을 시스템 프롬프트 뒤에 붙입니다(main.py:494). 사용자마다 달라지는 부분이므로 캐시 지점은 고정 부분과 가변 부분 사이에 두어야 합니다. 컨텍스트 엔지니어링 모듈의 "정적 컨텍스트를 앞에" 원칙과 연결하세요.

4.5 비용 최적화 (슬라이드 21)

슬라이드 고려 사항 슬라이드의 접근 방식 샘플 구현 빈틈 / 개선 과제
토큰 소비 관리 프롬프트 캐싱, 슬라이딩 윈도우/요약, CloudWatch 지표와 예산 경보 모델 라우팅: LOW는 Haiku, 그 외는 Sonnet. 메모리는 요약만 주입. 최종 응답은 3–6문장으로 제한(SYSTEM_PROMPT) 토큰 사용량 경보, 예산 경보 없음
적절한 크기 조정 Runtime 종량제, 계층형 보존, 테일 기반 샘플링 Runtime 종량제, DynamoDB PAY_PER_REQUEST, Lambda 256MB, 로그 2주 온라인 평가 샘플링 100%, Transaction Search 인덱싱 100%(cdk-stack.ts:427)
캐싱 및 재사용 Gateway로 도구 중앙화, ElastiCache, CloudFront Gateway에 도구를 모아 다른 에이전트도 재사용 가능(ADR-2) 도구 결과 캐시 없음 (get_process_info는 자주 바뀌지 않으므로 후보)

보여 줄 코드: 비용 라우팅 (model/load.py:15-30)

def load_model(priority: str = "MEDIUM") -> BedrockModel:
    model_id = AGENT_MODEL_ID          # Sonnet
    if priority == "LOW":
        model_id = FAST_MODEL_ID       # Haiku
    return BedrockModel(model_id=model_id)

설명 포인트: 1. ADR-8은 "단순 티켓을 약 10배 저렴하게"를 근거로 듭니다. 숫자보다 "비싼 추론은 필요할 때만" 이라는 원칙이 슬라이드 6(대리권은 필요할 때만)과 같은 구조라는 점을 짚습니다. 2. 라우팅 신호(priority)를 누가 정하는지가 공정성 문제와 연결됩니다(§2.4). 3. 모델 ID가 agentcore.json의 envVars에 있어서 코드 수정 없이 바꿀 수 있습니다.

개선 과제: 슬라이드의 "테일 기반 샘플링"을 샘플에 적용하면? - 지금은 온라인 평가가 모든 트레이스를 LLM 심판으로 채점합니다(100%). 평가 비용이 에이전트 실행 비용에 비례해 커집니다. - 1단계: samplingRate를 10–20%로 낮춤. - 2단계: Failed 티켓과 재발 티켓은 항상 평가하고 싶다면? 온라인 평가는 비율 샘플링이므로, 실패 트레이스는 ticket.id로 찾아 온디맨드 평가로 따로 돌리는 구성을 토론합니다. - 슬라이드의 계층형 보존(트레이스 7일, 지표 30일, 요약 1년)과 비교: 샘플은 Lambda 로그 2주, Memory 이벤트 30일, DLQ 14일입니다.

5. 아키텍처 설계 활동 (슬라이드 12–13)

5.1 진행 방식

슬라이드 노트대로 코딩이 아닌 설계 실습입니다. 이 샘플은 단일 에이전트이므로 정답지로 쓰지 말고, "이미 검증된 패턴의 재료 상자" 로 씁니다. 수강생이 각 마커에서 막히면 "IT 장애 에이전트에서는 이 문제를 어떻게 풀었나요?"라고 되묻습니다.

시나리오 요구 사항(슬라이드 13 노트): 감독되는 대리권, 멀티 에이전트(주문·추천·기술 지원·청구), PII·결제 정보, 가용성 99.9%, PCI-DSS.

5.2 마커별로 이 샘플에서 가져올 패턴

마커 논의 주제 (슬라이드 노트) 이 샘플에서 가져올 패턴 전자상거래로 옮길 때 바꿀 점

3 오케스트레이터 → 사용자 응답 검증, 콘텐츠 필터, 감사, SLA 결과가 비면 자동 종결 금지(main.py:577-581), 단계별 SSE 스트리밍(_stage_event) 출력 쪽 Guardrail 추가(샘플은 입력만). 카드 번호 등 PCI 데이터는 BLOCK
4 오케스트레이터 → 전문가 에이전트 간 통신, 장애 처리 도구 연결 실패 시 성능 저하 모드(get_all_mcp_clients_safe) 전문가 에이전트 하나가 죽어도 나머지로 응답(예: 추천 에이전트 장애 시 주문 조회는 계속). 회로 차단기
5 전문가 → 도구 도구 액세스 정책, VPC, 데이터 분류 도구별 Lambda + 최소 권한 IAM, Cedar 정책, 도구 입력 검증 Cedar로 "청구 에이전트는 billing_tool만" 정책. 결제 도구는 VPC 내부 + PrivateLink

5.3 활동 4개 영역별 모범 답안 골격

강사용 정리입니다. 수강생 발표 뒤 빠진 항목을 채워 주는 용도로 씁니다.

① 다중 에이전트 및 컨텍스트 설계 - 오케스트레이터는 분류만 하는 가벼운 모델(Haiku), 청구·기술 지원처럼 추론이 필요한 전문가는 Sonnet. 샘플의 load_model(priority)를 에이전트 단위로 확장한 형태입니다. - 컨텍스트 전략: 기록(Memory 요약, 샘플 ADR-4), 선택(Gateway 시맨틱 검색으로 필요한 도구만), 압축(요약 상위 N개), 분리(전문가마다 자기 도구와 자기 컨텍스트만).

② 프로덕션 아키텍처 - 에이전트별 Runtime(독립 확장, 세션 격리). 공통 도구는 하나의 Gateway에 모음. - 비동기 작업(환불 처리 등)은 샘플처럼 이벤트로 분리: SNS/SQS + DLQ, 결과는 EventBridge로 발행. - 선언형 구성(agentcore.json) + CDK 단일 배포로 시작하고, 규모가 커지면 공유 인프라 스택과 에이전트 스택을 분리(ADR-9의 트레이드오프).

③ 보안 설계 - 3개 인증 경계(샘플 docs/authentication-guide.md)를 그대로 적용: 사용자 → 오케스트레이터(Cognito JWT), 에이전트 → Gateway(Identity M2M), 외부 SaaS(3LO). - Cedar 정책은 LOG_ONLY로 시작해 위반 로그 확인 후 ENFORCE(ADR-7). - 감사 로그 1년 보존(PCI-DSS) → 샘플의 2주 보존과 대비해 "규정이 보존 기간을 결정한다"는 점을 강조.

④ 관찰성 및 평가 - 세션 수준 GoalSuccessRate(문제가 해결됐나), 트레이스 수준 Correctness·Helpfulness, 스팬 수준 ToolSelectionAccuracy(마커 5). 샘플의 평가기 4개가 이 세 수준을 모두 덮고 있습니다. - 샘플링은 10–20% + 실패·불만 세션은 온디맨드 평가. - 경보: 샘플의 DLQ 경보 외에 에이전트별 오류율, p95 지연, 토큰 사용량.

6. 모듈 요약과 지식 확인 (슬라이드 14–15)

6.1 요약 (2분)

학습 목표 2개를 이 샘플로 다시 말합니다. 1. WA에 부합하는 설계 전략을 사용한다: 이 샘플의 ADR 10개가 각각 어느 WA 요소의 결정인지 말할 수 있다. 2. WA 핵심 요소로 에이전틱 아키텍처를 평가한다: §3 체크리스트로 이 샘플의 빈틈(정책 LOG_ONLY, VPC 없음, 평가 100%, 실행 타임아웃 없음 등)을 찾을 수 있다.

6.2 보충 문제 (질문 시간용)

Q1. 이 샘플은 Policy Engine을 LOG_ONLY로 배포합니다. 그런데도 lookup_user 도구가 사용자 테이블에 쓰기를 할 수 없는 이유는?

정답: 도구 Lambda마다 IAM 역할이 따로 있고 lookup_user에는 grantReadData만 있기 때문(infra-construct.ts:360-361). 정책 계층과 IAM 계층이 겹치는 심층 방어. (보안)

Q2. 티켓 우선순위로 모델을 고르는 설계가 비용 외에 영향을 주는 WA 원칙은?

정답: 공정성. 요청자가 우선순위를 정하므로 부풀리거나, LOW 사용자 그룹이 체계적으로 낮은 품질을 받을 수 있음. 지속 가능성에도 긍정적 영향. (비용 최적화, 공정성)

Q3. 에이전트가 해결 코멘트를 만들지 못하면 이 샘플은 티켓을 어떻게 처리합니까? 왜 그렇게 합니까?

정답: Failed로 기록(main.py:577-581). 자리표시자 문구로 자동 종결하면 사람 검토가 필요한 티켓이 조용히 닫히기 때문. (신뢰성, 제어 가능성)

Q4. 과거 장애 수를 Memory 요약에서만 세지 않고 DynamoDB도 조회하는 이유는?

정답: SUMMARIZATION 요약은 비동기로 만들어져 직후 재제출된 티켓을 반영하지 못함. 강한 일관성이 필요한 수치는 DB에서 가져옴(main.py:149-179). (성능 효율성, 진실성)

Q5. 이 샘플을 Scoping Matrix의 Scope 2로 바꾸려면 가장 먼저 무엇을 바꿔야 합니까?

정답: create_change_request가 바로 적용(status: applied)하지 않고 승인 대기로 기록, 사람이 승인한 뒤 적용. (보안, 거버넌스)
