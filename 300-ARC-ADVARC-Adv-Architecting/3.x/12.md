## 1. 데이터 전송 비용  

데이터 전송 비용은 아키텍처 다이어그램에 보이지 않지만 청구서에서는 크게 나타납니다. 컴퓨팅을 최적화한 뒤에도 비용이 줄지 않는다면 대부분 여기가 원인입니다.

| 트래픽 경로 | 과금 | 절감 방법 |
|---|---|---|
| **같은 AZ 안** (프라이빗 IP) | 무료 | 통신이 잦은 구성 요소는 같은 AZ에 배치합니다. 단, 고가용성과의 트레이드오프를 고려해야 합니다. |
| **AZ 간** | 양방향 각각 약 $0.01/GB | 읽기 복제본과 캐시를 AZ별로 두고, AZ 인식 라우팅을 사용합니다. |
| **NAT Gateway** | 시간당 요금 + **처리 데이터 약 $0.045/GB** | S3와 DynamoDB는 **게이트웨이 엔드포인트(무료)**로 우회합니다. 그 밖의 서비스는 인터페이스 엔드포인트(시간당 요금 + 약 $0.01/GB)와 비교해 봅니다. |
| **리전 간** | 약 $0.02/GB | 복제 범위를 최소화합니다. CRR과 글로벌 테이블은 정말 필요한 데이터에만 적용합니다. |
| **인터넷 송신** | 구간별 요금 (월 100GB 무료) | **CloudFront**를 씁니다. AWS 오리진에서 CloudFront로 가는 전송은 무료이고, 캐시 적중률이 높을수록 송신량이 줄어듭니다. |
| **온프레미스로 송신** | 인터넷 요금 | 송신량이 많다면 **Direct Connect**의 송신 단가가 더 낮습니다. |

## 2. 스팟 인스턴스 모범 사례

스팟은 최대 90%까지 할인되지만, **2분 전 알림 후 회수될 수 있습니다.** 따라서 "중단을 견디는 아키텍처"가 전제 조건입니다.

| 모범 사례 | 내용 |
|---|---|
| **유연성 확보 (다양화)** | 여러 인스턴스 유형, 크기, 세대, **모든 AZ**에 걸쳐 용량 풀을 넓힙니다. 속성 기반 인스턴스 유형 선택(vCPU, 메모리 범위 지정)을 활용합니다. |
| **할당 전략** | **price-capacity-optimized**를 권장합니다. 중단 가능성이 낮은 풀 중에서 가장 저렴한 풀을 고릅니다. lowest-price는 중단이 잦아 권장하지 않습니다. |
| **Capacity Rebalancing** | ASG에서 활성화하면 **재조정 권장 신호**(중단 위험이 높아졌다는 신호)를 받았을 때 2분 알림을 기다리지 않고 미리 대체 인스턴스를 시작합니다. |
| **중단 처리** | IMDS(`spot/instance-action`)나 EventBridge 이벤트로 알림을 받습니다. 받으면 체크포인트를 남기고, 로드 밸런서에서 해제하고, 대기열 메시지를 반환합니다. |
| **온디맨드 혼합** | ASG 혼합 인스턴스 정책으로 **기본 용량은 온디맨드(또는 SP 적용)로, 초과분은 스팟으로** 구성합니다. |
| **사전 확인** | Spot placement score로 리전과 AZ별 확보 가능성을 확인합니다. |

**적합한 워크로드**: 상태 비저장 웹 계층, 배치 처리, CI/CD, 컨테이너(ECS, EKS, Karpenter), 빅데이터(EMR), ML 학습(체크포인트 사용)

**부적합한 워크로드**: 단일 인스턴스 DB, 상태 저장 레거시 앱, 중단을 허용하지 않는 장기 작업

## 3. 예약 인스턴스(RI) 세부 사항과 SP·RI 선택 기준

### Standard RI와 Convertible RI

| 구분 | Standard RI | Convertible RI |
|---|---|---|
| 최대 할인 | 약 72% | 약 66% |
| 속성 변경 | AZ, 크기, 네트워크 유형만 변경 가능 (같은 패밀리 안) | **패밀리, OS, 테넌시까지 교환 가능** (같거나 더 큰 가치로) |
| RI Marketplace 판매 | **가능** | 불가능 |

### 리전 범위 RI와 영역(AZ) 범위 RI

| 구분 | 리전 범위 | 영역 범위 |
|---|---|---|
| 할인 적용 | 리전 내 모든 AZ | 지정한 AZ만 |
| 인스턴스 크기 유연성 | **있음** (Linux, 기본 테넌시) | 없음 |
| **용량 예약** | **없음** | **있음** |

- 할인과 용량 확보를 함께 원한다면 **온디맨드 용량 예약(ODCR)과 리전 범위 RI 또는 Savings Plans를 조합**합니다. DR이나 이벤트 대비 용량 확보에 쓰는 패턴입니다.

### Savings Plans와 RI 선택 기준

| 상황 | 권장 |
|---|---|
| EC2, Fargate, Lambda 컴퓨팅 | **Savings Plans** (유연성이 필요하면 Compute SP, 최대 할인을 원하면 EC2 Instance SP) |
| RDS, ElastiCache, OpenSearch, Redshift | **RI** (Database Savings Plans 적용 범위는 최신 문서로 확인) |
| DynamoDB 프로비저닝 용량 | 예약 용량 (Reserved Capacity) |
| 특정 AZ의 용량 보장 필요 | 영역 범위 RI 또는 ODCR |
| 약정 기간 중 일부를 되팔 가능성 | Standard RI (Marketplace) |

- **적용 순서**: 청구 시 **RI가 먼저 적용되고, 남은 사용량에 Savings Plans가 적용**됩니다. 둘을 함께 구매할 때 중복으로 약정하지 않도록 주의합니다.
- **관리 지표**: 사용률(Utilization)과 커버리지(Coverage)를 Budgets로 모니터링합니다. 일반적인 목표는 사용률 95% 이상, 커버리지 70–80%입니다.

## 4. EBS 최적화

### gp2에서 gp3로 전환

| 항목 | gp2 | gp3 |
|---|---|---|
| GB당 가격 | 약 $0.10 | 약 $0.08 (**약 20% 저렴**) |
| 성능 모델 | **용량에 비례** (GB당 3 IOPS, 버스트 크레딧) | 용량과 무관하게 **기본 3,000 IOPS, 125MB/s** |
| 성능 조정 | IOPS를 늘리려면 용량을 늘려야 함 | **IOPS와 처리량을 독립적으로 프로비저닝** |

- 전환은 **Elastic Volumes**로 할 수 있으며 **다운타임이 없습니다.**
- gp2에서 IOPS 때문에 용량을 과다 할당했다면 gp3로 바꾸면서 용량까지 줄일 수 있어 절감 효과가 더 큽니다. 단, 볼륨 용량 축소는 직접 할 수 없어 데이터 이관이 필요합니다.
- io1을 사용 중이라면 io2(Block Express)도 검토합니다.

### 낭비 리소스 점검

| 대상 | 점검·조치 방법 |
|---|---|
| **미연결 볼륨** (available 상태) | Trusted Advisor, Compute Optimizer의 유휴 리소스 탐지로 찾습니다. 스냅샷을 남긴 뒤 삭제합니다. |
| **고아 스냅샷** | 삭제된 볼륨이나 AMI의 스냅샷입니다. **Data Lifecycle Manager(DLM)**로 보존 정책을 자동화합니다. |
| **장기 보관 스냅샷** | **EBS Snapshots Archive**로 옮기면 약 75% 저렴합니다. 최소 90일 보관, 복원에 24–72시간이 걸립니다. |
| **실수로 삭제하는 위험** | **Recycle Bin**으로 삭제된 스냅샷과 AMI를 일정 기간 복구할 수 있게 합니다. |
| **과다 프로비저닝 IOPS** | Compute Optimizer의 EBS 권장 사항을 따릅니다. |

## 5. S3 Storage Lens와 수명 주기 규칙의 함정

### S3 Storage Lens
- **조직 전체**의 S3 사용량과 활동을 한 대시보드로 봅니다(계정, 리전, 버킷, 접두사 단위).
- **무료 지표**와 **고급 지표**(유료: 활동 지표, 접두사 수준, 15개월 보관, CloudWatch 게시)가 있습니다.
- 비용 최적화에 바로 쓸 수 있는 지표:
  - **완료되지 않은 멀티파트 업로드** 바이트
  - **이전 버전(noncurrent version)** 바이트
  - 수명 주기 규칙이 없는 버킷
  - 액세스가 거의 없는 버킷(콜드 버킷)
- 접두사 단위로 액세스 패턴을 상세히 보려면 **S3 스토리지 클래스 분석**을 함께 씁니다.

### 수명 주기 규칙의 함정

| 함정 | 설명 | 대응 |
|---|---|---|
| **전환 요청 요금** | 객체 1,000건마다 전환 요금이 붙습니다. Glacier 계열로 갈수록 비쌉니다. | 작은 객체가 수백만 개라면 전환 요금이 저장 절감액보다 클 수 있습니다. 먼저 계산하거나, 객체를 묶은 뒤(tar, Parquet) 전환합니다. |
| **최소 과금 객체 크기** | Standard-IA, One Zone-IA는 **최소 128KB**로 과금합니다. | 128KB 미만 객체는 IA로 옮기지 않습니다. 현재 수명 주기는 기본적으로 128KB 미만 객체를 전환하지 않습니다. |
| **최소 보관 기간** | IA 30일, Glacier Instant·Flexible Retrieval 90일, Deep Archive 180일입니다. | 그 전에 삭제하거나 덮어쓰면 남은 기간도 과금됩니다. 수명이 짧은 데이터는 전환하지 않습니다. |
| **Glacier 객체당 오버헤드** | 객체마다 메타데이터 약 40KB가 추가로 저장됩니다(일부는 Standard 요금). | 작은 객체가 많으면 오버헤드 비중이 커집니다. 묶어서 아카이빙합니다. |
| **Intelligent-Tiering의 작은 객체** | 128KB 미만 객체는 모니터링되지 않고 항상 Frequent 요금으로 과금됩니다(모니터링 요금도 없음). | 작은 객체 위주라면 효과가 제한적입니다. |
| **보이지 않는 비용** | 버전 관리 버킷의 이전 버전, 완료되지 않은 멀티파트 업로드, 만료된 삭제 마커가 쌓입니다. | `NoncurrentVersionExpiration`, `AbortIncompleteMultipartUpload`, 만료된 삭제 마커 정리 규칙을 **모든 버킷의 기본 규칙**으로 넣습니다. |

## 6. 단위 비용(Unit Economics)과 FinOps 성숙도

### 왜 단위 비용인가
- 총 비용만 보면 "비용이 늘었다 = 나쁘다"로 오해합니다. **비즈니스가 성장하면 총 비용은 늘어나는 것이 정상**입니다.
- 비용을 비즈니스 지표로 나눈 **단위 비용**이 줄고 있다면 효율이 좋아지고 있는 것입니다.

| 단위 비용 예시 | 계산식 |
|---|---|
| 트랜잭션당 비용 | 월 서비스 비용 ÷ 월 트랜잭션 수 |
| 고객(테넌트)당 비용 | 고객별로 할당된 비용 ÷ 활성 고객 수 |
| GB당 처리 비용 | 데이터 파이프라인 비용 ÷ 처리량(GB) |
| API 호출당 비용 | API 계층 비용 ÷ 호출 수 |

- 덱 49–52번 슬라이드의 이미지 처리 앱($0.0006에서 $0.000176으로)이 바로 **트랜잭션당 비용**을 쓴 예입니다. 연결해서 설명하면 좋습니다.

### 비용 KPI 예시 (17번 슬라이드의 "효율성 KPI" 구체화)
- 태그가 지정된 지출 비율(할당 가능 비용 %)
- Savings Plans·RI 커버리지와 사용률
- 스팟과 Graviton 사용 비율
- 최신 세대 인스턴스 비율, gp3 비율
- 비프로덕션 환경의 업무 시간 외 중지 비율
- 단위 비용 추세(월별)

### FinOps 성숙도 (FinOps Foundation: Crawl / Walk / Run)

| 단계 | 특징 |
|---|---|
| **Crawl** | 기본 가시성 확보, 태깅 정책 수립, 수동 보고, 일부 약정 구매 |
| **Walk** | 쇼백·차지백 운영, 예산과 이상 탐지 자동화, 정기 적정 크기 조정 |
| **Run** | 단위 비용 기반 의사 결정, 최적화 자동화, 엔지니어링 프로세스에 비용 내재화(설계 리뷰, CI/CD 비용 검사) |

### 구현 도구
- **CUR 2.0 + Athena**: 단위 비용 계산의 원천 데이터입니다. 비즈니스 지표와 조인합니다.
- **Cost Categories**: 계정, 태그, 서비스를 비즈니스 단위로 묶는 규칙입니다.
- **Cloud Intelligence Dashboards** (CUDOS, KPI Dashboard 등): QuickSight 기반의 AWS 제공 대시보드 프레임워크입니다.
- **Billing Conductor**: 사내 재청구용 요율을 따로 정의할 때 씁니다.
