
##### VPC 간 연결 방식 선택

| 기준       | VPC 피어링 | Transit Gateway | Cloud WAN | VPC 공유(RAM) | PrivateLink | VPC Lattice |
|-----------|------------|---|---|---|---|---|
| 연결 단위  | VPC↔VPC    | 네트워크(L3) | 글로벌 네트워크 | 서브넷 공유 | 서비스(L4) | 서비스(L7) |
| 전이 라우팅 | ✗ | ✓ | ✓ | 해당 없음 | 해당 없음 | 해당 없음 |
| CIDR 중복  | ✗ | ✗ | ✗ | 해당 없음 | ✓ | ✓ |
| 방향       | 양방향 | 양방향 | 양방향 | 같은 VPC | 단방향 | 단방향 |
| 비용 구조   | 데이터 전송만<br>(같은 AZ는 무료) | 연결 시간 + GB당 처리 요금 | 코어 네트워크 엣지 + 처리 요금 | 추가 없음 | 엔드포인트 시간 + GB | 서비스 + 요청 + GB |
| 적합한 경우 | 소수, 대용량, 저비용 | 다수 VPC + 하이브리드 허브 | 다중 리전, 정책 기반 | 중앙 네트워크 팀 운영 | SaaS 형태, 서비스 노출 | 마이크로서비스 간 연결, 인증 |

##### 랜딩 존 네트워크

```text
[온프레미스 데이터 센터]
        │
   DX / VPN                  ← 3장: 경계(들어오는 문)
        │
 [Network 계정]
   DX 게이트웨이
        │ Transit VIF
   Transit Gateway           ← 접점(로비)
   ├─ 라우팅 테이블: Prod   → Prod VPC들 (워크로드 계정)
   ├─ 라우팅 테이블: Dev    → Dev VPC들  (워크로드 계정)
   ├─ 라우팅 테이블: Shared → 공유 서비스 VPC (DNS, 엔드포인트)
   └─ 이그레스/검사 VPC     → 인터넷, 방화벽
                             ← 5장: 내부(복도와 출입문)
```

경계와 내부를 따로 설계하면 실제로 이런 문제가 생깁니다.

| 결정 사항 | 경계(3장)와 내부(5장)가 엮이는 지점 |
|-------------------------------------|---|
| 온프레미스가 Dev VPC에 접근해도 되는가? | DX로 들어온 경로가 어느 TGW 라우팅 테이블로 전파되는지가 이를 결정합니다. 경계 설정이 아니라 내부 라우팅 설계의 문제입니다. |
| IP 주소 계획 | 온프레미스 대역과 VPC 대역이 겹치면 DX를 연결해도 통신할 수 없습니다. 처음부터 **전체 IP 계획(IPAM)**을 함께 세워야 합니다. |
| 경로 수 제한 | VPC가 늘어나면 DX로 광고할 접두사가 많아집니다. DX의 광고 개수 제한(3장)이 VPC 대역을 요약해서 설계(5장)하도록 강제합니다. |
| DNS | 온프레미스에서 AWS 서비스 이름을 조회하려면 Resolver 엔드포인트(3장)가 필요합니다. 이것을 공유 서비스 VPC(5장)에 둡니다. |
| 보안 검사 | 온프레미스 트래픽도 방화벽을 거치게 하려면, DX 경로가 검사 VPC를 지나도록 TGW 라우팅을 짜야 합니다. |
| 새 계정 추가 | 새 워크로드 계정이 생기면 DX를 새로 깔지 않습니다. TGW에 VPC만 연결하면 기존 경계를 그대로 씁니다. 이것이 표준화의 효과입니다. |
