### Account Factory

1. 프로비저닝 방법

| # | 방법 | 수행 방식 | 적합한 상황 |
|---|---|---|---|
| ① | Control Tower 콘솔의 Account Factory | Organization 화면에서 Create account를 선택하고 이메일, 표시 이름, IAM Identity Center 사용자, 대상 OU를 입력합니다. | 관리자가 계정을 가끔, 소량으로 만들 때 |
| ② | Service Catalog 콘솔 (셀프 서비스) | Identity Center 최종 사용자가 Service Catalog에서 AWS Control Tower Account Factory 제품을 실행합니다. | 권한을 받은 현업 팀이 승인된 템플릿으로 직접 계정을 만들 때 (모듈 슬라이드 S45~S46에서 다룬 방식) |
| ③ | Service Catalog API/CLI | `aws servicecatalog provision-product`로 Account Factory 제품을 프로그래밍 방식으로 호출합니다. | 사내 포털이나 ITSM(ServiceNow, Jira 등)의 승인 워크플로와 연동할 때 |
| ④ | Account Factory for Terraform (AFT) | 계정 요청을 Terraform 코드로 Git에 커밋하면 파이프라인이 Service Catalog를 호출해 계정을 만들고, 이어서 사용자 지정 설정까지 적용합니다. | 대규모·반복 발급, GitOps 기반 운영. 요청을 큐에 넣어 차례로 처리하므로 여러 계정을 한꺼번에 요청할 수 있습니다. |
| ⑤ | Account Factory Customization (AFC) | Service Catalog 제품으로 등록한 블루프린트(CloudFormation 또는 Terraform)를 선택해 계정 생성 시점에 리소스를 함께 배포합니다. | 콘솔 방식을 유지하면서 표준 VPC, IAM 역할, 보안 설정을 기본으로 넣고 싶을 때 |
| ⑥ | 사용자 지정 자동화 (Lambda + AWSControlTowerExecution 역할) | 관리 계정의 Lambda가 멤버 계정의 실행 역할을 수임해 후속 설정을 자동화합니다. | 생성 이후의 구성을 직접 코드로 제어하려 할 때 (모듈 노트 S39, S44에서 언급한 방식) |

- 계정 생성과 함께 사용하는 자동화 프레임워크
  - Customizations for Control Tower (CfCT): 계정 생성 같은 수명 주기 이벤트가 발생하면 CloudFormation 템플릿과 SCP를 자동으로 배포합니다. 계정을 만드는 도구가 아니라 생성 직후의 기준선(baseline) 설정을 맡습니다.
  - Landing Zone Accelerator on AWS (LZA): 설정 파일로 계정, 네트워크, 보안 구성을 한꺼번에 정의하는 솔루션입니다. 규제 산업에서 많이 씁니다.

### AFT Vs CfCT

- AFT는 "계정을 만들고 설정하는 파이프라인"
- CfCT는 "이미 만들어진 계정에 표준 설정을 배포하는 파이프라인"

| 항목      | AFT (Account Factory for Terraform)  | CfCT (Customizations for Control Tower) |
|----------|--------------------------------------|-----------------------------------------------------|
| 주 목적   | 계정 발급(vending)과 사용자 지정 설정    | 계정과 OU에 사용자 지정 설정 배포 |
| 계정 생성 | ✅ 가능합니다 (내부적으로 Account Factory의 Service Catalog 제품 호출) | ❌ 불가능합니다 (다른 방법으로 만든 계정이 대상) |
| IaC 언어 | Terraform (+ Python, 셸 스크립트 실행 가능) | CloudFormation 템플릿 + SCP(JSON) |
| 설치 위치 | 별도의 AFT 관리 계정 (권장 사항) | Control Tower 관리 계정의 홈 리전 |
| 설정 소스 | Git 저장소 4개 (GitHub, GitLab, Bitbucket 등. 신규 고객은 CodeCommit 사용 불가) | `manifest.yaml` 하나와 템플릿·정책 파일 (S3 버킷 또는 Git 저장소) |
| 실행 트리거 | 계정 요청 코드 커밋, 사용자 지정 설정 저장소 변경 | Control Tower 수명 주기 이벤트(`CreateManagedAccount` 등), 매니페스트 변경 |
| 배포 메커니즘 | 계정별 CodePipeline/CodeBuild에서 `terraform apply` 실행 | CloudFormation StackSets(리소스), Organizations API(SCP) |
| 배포 대상 지정 | 계정 단위 (전체 공통 설정 + 계정별 설정) | OU 단위나 계정 단위 (매니페스트의 `deployment_targets`) |
| SCP 관리 | 직접 제공하지 않습니다 (Terraform 코드로 따로 구현) | ✅ 기본 기능입니다 |
| Terraform 상태 관리 | 필요합니다 (OSS는 S3+DynamoDB, 또는 HCP Terraform/Enterprise) | 해당 없음 (CloudFormation이 상태 관리) |
| 대량 처리 | 요청을 SQS FIFO 큐에 넣어 차례로 처리하므로 여러 계정을 한 번에 요청할 수 있습니다 | 이벤트가 생길 때마다 처리합니다 |
| 학습 곡선 | 높습니다 (Terraform, 파이프라인 4종, 상태 관리) | 중간입니다 (CloudFormation, 매니페스트 문법) |
| 비용 | 솔루션은 무료입니다. 하위 리소스 비용이 들고, 특히 AFT VPC의 NAT 게이트웨이와 VPC 엔드포인트 비용이 큽니다 | 솔루션은 무료입니다. 하위 리소스 비용(파이프라인, Step Functions 등)만 듭니다 |

### 기존 AWS 계정의 AWS Control Tower 등록을 자동화(p50)

AWSAdministratorAccess는 Control Tower가 랜딩 존을 만들 때 IAM Identity Center에 생성하는 **권한 세트(Permission Set)**입니다. 여기에는 AWS 관리형 정책 **AdministratorAccess**가 붙어 있습니다. 즉 관리 계정의 모든 리소스에 대해 모든 작업을 허용하는 관리자 권한입니다.

1. 실제 정책 내용

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    }
  ]
}
```
- SCP는 관리 계정에 적용되지 않습니다. 그래서 관리 계정에서 이 권한은 사실상 제한이 없는 전체 권한입니다.

2. "임시 자격 증명"의 정체

    - 1. 권한 세트를 계정에 할당하면 해당 계정에 AWSReservedSSO_AWSAdministratorAccess_<랜덤값> 형태의 IAM 역할이 자동으로 생깁니다.
    - 2. Identity Center 포털에서 관리 계정의 AWSAdministratorAccess를 선택하고 **"Command line or programmatic access"**를 누르면, 이 역할을 수임한 STS 임시 자격 증명이 발급됩니다.
    ```text
    export AWS_ACCESS_KEY_ID=ASIA...
    export AWS_SECRET_ACCESS_KEY=...
    export AWS_SESSION_TOKEN=...
    ```
    - 3. 세션 기간은 권한 세트 설정을 따릅니다. 기본값은 1시간이고 최대 12시간까지 늘릴 수 있습니다. 장기 액세스 키가 아니라서 만료되면 자동으로 무효가 됩니다.
    - Control Tower는 기본적으로 이 권한 세트를 AWSControlTowerAdmins 그룹에 할당합니다.

3. 등록 스크립트에 이 권한이 필요한 이유

enroll_script.py는 관리 계정에서 다음 작업을 수행합니다.

| 단계 | 호출하는 서비스 | 필요한 권한 |
|---|---|---|
| 대상 계정과 OU 검증 | AWS Organizations | `organizations:Describe*`, `organizations:List*` |
| 대상 계정에 역할 생성 | CloudFormation StackSets (자동 배포) | `cloudformation:CreateStackSet`, `cloudformation:CreateStackInstances` 등 |
| 계정 등록 | Service Catalog (Account Factory 제품 시작) | `servicecatalog:ProvisionProduct` 등 |
| SSO 사용자 생성 | IAM Identity Center | `sso:*`, `identitystore:*` |

여러 서비스를 넘나들며 조직 전체에 영향을 주는 작업이라 관리자 권한을 쓰도록 안내하는 것입니다.

4. 헷갈리기 쉬운 두 역할 구분

| 구분 | AWSReservedSSO_AWSAdministratorAccess_xxx | AWSControlTowerExecution |
|---|---|---|
| 위치 | **관리 계정** | **대상(등록할) 계정** |
| 생성 주체 | Identity Center 권한 세트 | 스크립트가 StackSets로 생성 |
| 사용자 | 스크립트를 실행하는 사람 | Control Tower 서비스 |
| 신뢰 대상 | Identity Center(SAML) | 관리 계정 (`arn:aws:iam::<관리계정ID>:root`) |
| 연결 정책 | AdministratorAccess | AdministratorAccess |

즉 AWSAdministratorAccess는 스크립트를 실행하는 사람의 권한입니다. AWSControlTowerExecution은 등록 후 Control Tower가 대상 계정을 관리할 때 쓰는 역할입니다.

5. 아키텍처 관점 주의점

- 범위가 매우 넓은 권한이므로 등록 작업에만 짧게 쓰는 것을 권장합니다. 모듈 2의 모범 사례인 "관리 계정 관리자 권한의 할당 제한"과 같은 맥락입니다.
- 자격 증명을 EC2에 붙여넣을 때는 셸 기록이나 파일에 남지 않도록 주의합니다. 작업이 끝나면 세션을 종료하는 것이 안전합니다.
