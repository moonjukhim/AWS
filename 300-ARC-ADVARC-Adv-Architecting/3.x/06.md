### 1. 핵심 축: 운영 책임과 제어권의 스펙트럼

```text
 AWS가 더 많이 관리 ◀──────────────────────────────────────▶ 고객이 더 많이 제어

 Lambda │ ECS Express Mode │ ECS on Fargate │ ECS Managed Instances │ ECS on EC2
                           │ EKS Auto Mode  │ EKS + Fargate        │ EKS 관리형/자체 노드 │ EKS Hybrid Nodes / EKS-D
```

| 신규 옵션              |        시점 | 아키텍처적 의미 |
|-----------------------|------------|---|
| ECS Managed Instances | 2025년 9월  | EC2의 모든 기능(인스턴스 유형, GPU 등)을 쓰면서 프로비저닝·패치·스케일링은 AWS가 맡습니다. “Fargate는 제약이 많고 EC2는 운영이 무겁다”는 고전적 딜레마의 해법입니다. |
| ECS Express Mode | 2025년 11월 | 도메인, ALB(최대 25개 서비스 공유), 오토스케일링을 자동 구성합니다. App Runner는 2026년 4월 30일부터 신규 고객을 받지 않으며, AWS는 그 대안으로 Express Mode를 권장합니다. |
| EKS Auto Mode | 2024년 12월 | 컨트롤 플레인뿐 아니라 데이터 플레인(노드, 오토스케일링, LB, 스토리지, GPU)까지 AWS가 관리합니다. 슬라이드 51 |
| EKS Capabilities (Argo CD, ACK, kro) | re:Invent 2025 | GitOps와 AWS 리소스 관리를 AWS가 관리하는 플랫폼 계층으로 제공합니다. 플랫폼 엔지니어링 관점의 핵심입니다. |
| EKS Hybrid Nodes | 2024년 | 온프레미스·엣지 노드를 EKS 컨트롤 플레인에 연결합니다. 슬라이드 51의 하이브리드 시나리오를 갱신할 수 있습니다. |

### 2. 의사결정 프레임워크

| 기준         | ECS 쪽으로 기우는 신호 | EKS 쪽으로 기우는 신호 |
|-------------|---|---|
| 팀 역량·조직 | 작은 팀, AWS 중심, 플랫폼 팀 없음 | 이미 K8s 역량 보유(시나리오의 인수한 스타트업), 플랫폼 팀 존재 |
| 이식성 요구 | AWS 안에서만 운영 | 멀티클라우드·온프레미스 일관성, K8s API 표준 필요 |
| 생태계 | AWS 네이티브 통합(IAM, ALB, CloudWatch)으로 충분 | Helm, Operator, 서비스 메시, Karpenter, KEDA 등 CNCF 도구 필요 |
| 운영 부담 | 업그레이드 주기를 신경 쓰고 싶지 않음 | 연 3~4회 K8s 버전 업그레이드를 감당할 수 있음(Extended Support 비용 주의) |
| 워크로드 특성 | 웹·API·배치 위주 | ML/GPU 스케줄링, 복잡한 스테이트풀 워크로드, 멀티테넌트 플랫폼 |
| 비용 구조 | 컨트롤 플레인 요금 없음 | 클러스터당 컨트롤 플레인 요금, 대신 밀도 최적화 여지가 큼 |


##### 2-2. 컴퓨팅 선택 결정 트리 (예시)

```text
컨테이너가 꼭 필요한가? ── 아니오 → 이벤트 중심·짧은 실행이면 Lambda 검토
        │예
K8s API·생태계가 필요한가? ── 예 → EKS
        │아니오                    ├ 노드 관리를 맡기고 싶다 → EKS Auto Mode
        ▼                         ├ 격리 우선·소규모 → EKS + Fargate
       ECS                        └ 세밀한 제어·특수 하드웨어 → 관리형 노드 그룹 / Karpenter
        ├ 가장 빨리 웹/API 배포 → ECS Express Mode
        ├ 서버 관리 없이, 작업별 격리 → ECS on Fargate (+ Fargate Spot)
        ├ GPU·특정 인스턴스가 필요하지만 운영은 맡기고 싶다 → ECS Managed Instances
        └ 완전한 제어·최대 밀도·RI/SP 극대화 → ECS on EC2 (용량 공급자 + ASG)
```

# AWS Well-Architected Framework — 컨테이너 관련 항목 체크리스트

> Well-Architected Framework 본문(6개 원칙) 중 컨테이너 워크로드와 직접 관련된 모범 사례(BP)

---

## 1. 운영 우수성 (OPS)

| ☐ | BP | 컨테이너에서 확인할 항목 |
|---|---|---|
| ☐ | **OPS04-BP02** 애플리케이션 텔레메트리 구현 | Container Insights, FireLens/Fluent Bit로 STDOUT 로그 수집 |
| ☐ | **OPS04-BP05** 분산 추적 구현 | ADOT/X-Ray로 마이크로서비스 간 호출 추적 |
| ☐ | **OPS05-BP01** 버전 관리 | Dockerfile, 태스크 정의, Helm 차트, 매니페스트를 Git으로 관리 |
| ☐ | **OPS05-BP03** 구성 관리 시스템 | 환경별 설정 분리(Helm values, SSM Parameter Store) |
| ☐ | **OPS05-BP04** 빌드·배포 관리 시스템 | CodeBuild, CodePipeline, GitOps(Argo CD, Flux) |
| ☐ | **OPS05-BP05** 패치 관리 | 부모 이미지에 패치가 나오면 자식 이미지 자동 재빌드. EKS 노드 AMI 업데이트 |
| ☐ | **OPS05-BP06** 설계 표준 공유 | 조직 표준 **골드/부모 이미지** |
| ☐ | **OPS05-BP08** 다중 환경 사용 | 같은 이미지를 개발, 스테이징, 운영으로 승격 |
| ☐ | **OPS05-BP10** 통합과 배포 완전 자동화 | 이미지 빌드 → 스캔 → push → 배포까지 사람 손 없이 진행 |
| ☐ | **OPS06-BP03** 안전한 배포 전략 | ECS 블루/그린, 카나리, 선형 배포. Kubernetes 롤링, Argo Rollouts |
| ☐ | **OPS06-BP04** 테스트와 롤백 자동화 | ECS deployment circuit breaker와 자동 롤백, CloudWatch 알람 연동 |

## 2. 보안 (SEC)

| ☐ | BP | 컨테이너에서 확인할 항목 |
|---|---|---|
| ☐ | **SEC02-BP02** 임시 자격 증명 사용 | ECS **태스크 역할**, EKS **Pod Identity**/IRSA. 액세스 키를 하드코딩하지 않음 |
| ☐ | **SEC02-BP03** 비밀을 안전하게 저장하고 사용 | Secrets Manager/SSM을 태스크 정의 `secrets`로 주입. Secrets Store CSI Driver |
| ☐ | **SEC03-BP02** 최소 권한 부여 | 태스크 역할과 **실행 역할 분리**. EKS 액세스 항목과 RBAC |
| ☐ | **SEC04-BP01** 서비스·애플리케이션 로깅 구성 | EKS 컨트롤 플레인 감사 로그, ECS 태스크 로그, CloudTrail |
| ☐ | **SEC05-BP01** 네트워크 계층 생성 | 태스크와 파드는 프라이빗 서브넷, ALB는 퍼블릭 서브넷 |
| ☐ | **SEC05-BP02** 계층 내 트래픽 흐름 제어 | awsvpc의 **태스크별 보안 그룹**, EKS 파드용 보안 그룹과 NetworkPolicy |
| ☐ | **SEC06-BP01** 취약점 관리 | ECR + **Inspector 고급 스캔**(지속 스캔) |
| ☐ | **SEC06-BP02** 강화된 이미지로 컴퓨팅 프로비저닝 | 최소, distroless 베이스 이미지, non-root, 골드 이미지 |
| ☐ | **SEC06-BP03** 수동 관리와 대화형 접근 축소 | SSH 대신 **ECS Exec**/SSM. Fargate 사용 |
| ☐ | **SEC06-BP04** 소프트웨어 무결성 검증 | **이미지 서명**(ECR 관리형 서명, Notation/Cosign)과 어드미션 검증(Kyverno) |
| ☐ | **SEC06-BP05** 컴퓨팅 보호 자동화 | **GuardDuty 런타임 모니터링**(ECS, EKS, Fargate) |
| ☐ | **SEC11-BP02** 수명 주기 전반에서 테스트 자동화 | CI 단계의 이미지 스캔, 매니페스트 스캔(checkov) |
| ☐ | **SEC11-BP05** 패키지·의존성 서비스 중앙화 | 프라이빗 ECR, **pull-through cache**, CodeArtifact |
| ☐ | **SEC11-BP06** 소프트웨어를 프로그래밍 방식으로 배포 | 파이프라인으로만 배포. 수동 `kubectl apply` 금지 |
| ☐ | **SEC11-BP07** 파이프라인 보안 속성 정기 평가 | 빌드 인프라 최소 권한, **태그 불변성** |
